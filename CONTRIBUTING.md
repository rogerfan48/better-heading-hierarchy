# Contributing

Thanks for taking the time. Bug reports, feature ideas and pull requests are all welcome.

## Reporting a bug

Please include:

- Your Obsidian version, operating system, and the plugin version.
- Whether it happens in Reading view, in the editor, or both.
- A **minimal note** that reproduces it — the raw Markdown, not a screenshot of it. Heading-related
  bugs almost always come down to a specific structure (a skipped level, a heading inside a callout,
  a fenced code block), so the source text is the useful part.
- What you expected to see, and a screenshot of what you actually saw.

Also worth checking first: whether the problem still occurs with other plugins disabled and with the
default Obsidian theme. Guide lines are drawn on top of your theme's spacing, so a theme with unusual
block margins can be the actual cause.

## Development setup

Requires [Node.js](https://nodejs.org) 18 or newer.

```sh
git clone https://github.com/rogerfan48/better-heading-hierarchy.git
cd better-heading-hierarchy
npm install
```

The easiest way to test is to work directly inside a real vault. Clone into (or symlink the repo to)
`<test vault>/.obsidian/plugins/better-heading-hierarchy/`, then:

```sh
npm run dev     # rebuild main.js on every change, and compile the stylesheet once
```

Reload Obsidian (`Ctrl`/`Cmd` + `R`) to pick up a rebuild. The
[Hot Reload](https://github.com/pjeby/hot-reload) plugin does this automatically.

### Available scripts

| Script | What it does |
| --- | --- |
| `npm run dev` | Compile the stylesheet, then watch and rebuild `main.js`. |
| `npm run build` | Compile the stylesheet, type-check, and produce a production `main.js`. |
| `npm run css` | Compile `styles.scss` into `styles.css`. |
| `npm run lint` | Run ESLint over the TypeScript sources and build scripts. |

Run `npm run build` and `npm run lint` before opening a pull request.

## Project layout

| Path | Purpose |
| --- | --- |
| `main.ts` | Plugin entry point, settings, and the settings tab. |
| `src/settings.ts` | Settings interface and defaults. |
| `src/hierarchy.ts` | Pure functions that turn Obsidian's metadata cache into per-block depths. |
| `src/reading-view.ts` | Markdown post-processor for Reading view. |
| `src/live-preview.ts` | CodeMirror 6 view plugin for Live Preview and Source mode. |
| `styles.scss` | Source of truth for all styling. **Edit this, not `styles.css`.** |
| `styles.css` | Generated by `npm run css`; committed because Obsidian loads it directly. |
| `src/snippet.ts` | Writes and enables the companion snippet from the settings tab. |
| `snippets/` | The companion snippet. Bundled into `main.js` as text by esbuild, not shipped as a release asset. |

## Style notes

Two conventions matter more than the rest, because Obsidian's plugin review checks for them:

- **No `!important`, and no `:has()` in `styles.css`.** Anything the user might want to change should
  be a `--rgh-*` CSS variable instead. Personal or theme-specific styling belongs in `snippets/`,
  which is not part of a release.
- **Follow the [Obsidian plugin guidelines](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines).**
  In particular: sentence case for anything shown in the UI, no plugin name as a settings heading,
  and prefer `activeDocument` over `document` when reaching for a global.

Indentation is tabs, matching `.editorconfig`.

## Releasing

Maintainers only:

```sh
npm version patch   # or minor / major
git push --follow-tags
```

`npm version` runs `version-bump.mjs`, which syncs `manifest.json` and adds an entry to
`versions.json`. Pushing the tag triggers `.github/workflows/release.yml`, which builds the plugin,
attaches `main.js`, `manifest.json` and `styles.css` to a GitHub release, and attaches a build
provenance attestation to each of them.

Give the release a description before publishing it — Obsidian's plugin directory surfaces release
notes to users, and an empty release is flagged in the plugin scorecard.
